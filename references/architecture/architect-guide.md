# 系统架构师专家指南

> 整合系统设计、技术选型与技术路线规划的综合架构设计参考。
>
> 架构深度技术（高可用/高并发/分布式/安全架构）详见 [architecture-anti-patterns.md](architecture-anti-patterns.md)。

- 技术选型
- 系统演进
- 技术路线规划

### 架构模式

| 模式 | 适用场景 | 权衡 |
|---------|----------|------------|
| **微服务** | 独立扩展、团队自治 | 复杂度、分布式挑战 |
| **事件驱动** | 异步处理、解耦 | 最终一致、调试难 |
| **DDD** | 复杂领域 | 学习曲线、过度设计风险 |
| **CQRS** | 读写分离 | 复杂度、一致性管理 |
| **分层** | 简单应用 | 可能演变为单体 |
| **六边形** | 可测试性、可移植性 | 初始复杂度 |

## 工作流

### 1. 需求理解阶段

提供架构方案前，需理解：

```
┌─────────────────────────────────────────────────────────┐
│            需求理解                    │
├─────────────────────────────────────────────────────────┤
│ 业务场景                                       │
│   • 本系统解决什么问题？                 │
│   • 核心用户是谁？                              │
│                                                          │
│ 非功能需求                              │
│   • 性能要求？                            │
│   • 可用性目标？                                │
│   • 安全要求？                               │
│   • 预期规模？                                      │
│                                                          │
│ 技术约束                                    │
│   • 团队对技术栈的熟悉度？                    │
│   • 遗留系统集成？                                                          │
│                                                          │
│ 时间与资源                                       │
│   • 项目时间线？                                    │
│   • 团队规模与技能水平？                                                          │
│                                                          │
│ 未来演进                                         │
│   • 3-6 个月内的业务扩张？                    │
└─────────────────────────────────────────────────────────┘
```

### 2. 方案设计阶段

提供 2-3 个架构选项，每个包含：

```
选项 A：[名称]
├── 架构图
│   └── 系统分层、模块划分、数据流
├── 技术选型
│   └── 每个选择的理由
├── 优点
│   └── 优势
├── 缺点
│   └── 劣势
├── 实施成本
│   └── 开发工作量、学习曲线
└── 推荐
    └── 为何选此方案？
```

### 3. 细节澄清阶段

方案选定后：

```
├── 模块设计
│   └── 职责划分、接口定义
├── 数据模型
│   └── 关键实体、数据流路径
├── 技术细节
│   └── 关键实施建议
├── 风险点
│   └── 潜在风险、缓解措施
└── 实施路线
    └── 开发顺序、里程碑
```

## 架构设计原则

### 核心原则

1. **简洁优先**：简单方案可行时，不要引入复杂度
2. **演进式设计**：架构应平稳演进
3. **团队能力匹配**：考虑团队对技术栈的熟悉度
4. **可观测性**：为日志、监控、链路追踪而设计
5. **成本意识**：平衡技术收益与成本

### 技术选型指南

| 优先级 | 前端 | 后端 | 说明 |
|----------|----------|---------|-------|
| 1 | Vue 3 | Rust | 团队熟悉度 / 性能 |
| 2 | React 18 | Python | 生态 / 快速开发 |
| 3 | 其他 | Java | 企业级 |

**强制**：所有前端项目必须使用 TypeScript。

### 应避免的陷阱

- [ ] 无理由追逐技术趋势
- [ ] 盲目复制大厂架构
- [ ] 忽视运维复杂度
- [ ] 过早优化
- [ ] 与其他团队孤立设计

## 持续改进

讨论现有系统时：

1. **理解现状**
   - 当前架构
   - 技术债
   - 痛点

2. **评估理由**
   - 为何这样设计？
   - 当时存在什么约束？

3. **渐进式重构**
   - 避免"推倒重来"
   - 增量改进
   - 平衡短期与长期

4. **量化预期**
   - 可衡量的改进目标
   - 风险评估
   - 回滚计划

| 文档 | 内容 |
|----------|---------|
