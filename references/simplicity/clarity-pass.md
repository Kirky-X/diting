# Clarity Pass（清晰化重写协议）

> 来源：合并自已退役的 code-simplifier skill（2026-09-12，经所有者批准的 skill 合并）。
> 本协议是 diting Engine C（Simplicity/Refinement）在"写码后简化"场景的执行细则，
> 与 sweep-guide 的 auto-fix 同意门、Fix-Class 分级配合使用。

## 触发场景

- 用户明确要求：simplify / clean up / 精简 / 清理 / refactor for readability
- diting 审查后的 Refinement Pass 需要动手改码时
- 多文件功能实现完成后，用户同意做一次清晰化收尾

**不触发**：用户在调试/迭代 bug；用户明说"别重构"；临时原型/spike/迁移脚本；仅单行改动（配置值、常量微调）。

## 安全前提（改写前强制，缺一不可）

1. `git status --porcelain` 检查工作区：若有**不属于本任务**的未提交改动，先请用户 commit 或明确排除，**严禁**把用户改动卷进重写范围。
2. 用 `git diff` / `git diff --staged`（或用户显式指定的文件清单）定界范围——只处理本任务修改过的代码，绝不外溢（规则3 外科手术式修改）。
3. 失败回滚手段 = 仅对本 skill 改过的文件做 `git checkout -- <file>`；禁止全库 checkout/reset。
4. 无测试覆盖的文件：先跑 lint/type-check 并人工走查关键路径，结果标注 `needs-review`。

## 简化优先队列（按风险升序，逐级执行）

| 级 | 手段 | 风险 |
|---|---|---|
| 1 | 死代码清除：未用变量、不可达分支、注释掉的代码 | 零 |
| 2 | 改名：歧义命名 → 自文档化命名 | 低 |
| 3 | 降嵌套：卫语句提取、早返回 | 低 |
| 4 | 条件简化：复杂布尔逻辑 → 更清晰的模式 | 中 |
| 5 | 去重复：提取重复逻辑为 helper（仅当真的降复杂度，不是降行数） | 中 |
| 6 | 抽象扁平化：删除无价值的包装层/适配层/间接层 | 高 |

**停止条件**：继续改就需要理解代码本身揭示不了的业务上下文时立即停止——绝不猜业务意图（规则7）。

## 语言启发式

遵循项目 linter 配置与周边代码风格（规则11 惯例优先）；通用准则：一函数一事、避免魔数、参数 ≤3、禁嵌套三元（用 match/switch/if-else）、清晰优先于简短。

## 验证门槛（全部客观可查）

- [ ] 最大嵌套深度不升（数 `if`/`for`/`match` 层数）
- [ ] 无新依赖
- [ ] 无新 public API 面
- [ ] 既有测试全过
- [ ] lint/type-check 无新告警

失败处理：测试挂了且原因显而易见 → 修一次；不明显 → **回滚该处改动**，记录 `skipped — broke existing behavior`（规则12）。同一处重试 ≤1 次（规则20）。

## 报告格式（必须带 Risk 字段）

| Change | Before | After | Reason | Risk |
|--------|--------|-------|--------|------|
| 提取卫语句 | 3 层嵌套 if | 早返回 | 降嵌套 | none |

Risk 档：**none** / **low**（逻辑不变但结构变）/ **needs-review**（微妙行为依赖）。跳过项与原因必须出现在报告里。

## 过度简化反模式（这些不是简化）

| 反模式 | 为什么坏 | 改为 |
|---|---|---|
| 嵌套三元 | 难读难调 | match/switch/if-else |
| 密集单行 | 拿可读性换行数 | 拆命名中间步骤 |
| 删光注释 | 丢意图和 why | 保留解释非显然决策的注释 |
| 合并不相关函数 | 造 god-function | 保持单一职责 |
| 内联有益抽象 | 丢自文档结构 | 保留助理解的抽象 |
| 过早泛化 | 为假想未来加复杂度 | 简单解决当前问题 |

## 与审查的分工

- diting 审查模式（Engine A/B）：只识别与建议，不改码
- Clarity Pass（本协议）：审查之后动手改码，走上述安全前提与验证门槛
